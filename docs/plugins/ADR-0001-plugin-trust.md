# ADR-0001. Внешние плагины Backpack: процесс, IPC и модель доверия

Статус: принято (Phase 4D, 2026-10-29). Заменяет прежний запрет на внешние исполняемые плагины. Темы и профили по-прежнему не исполняют код.

## Контекст

Нужно импортировать внешние функции (не только каталог встроенных переключателей), не ослабляя приватность ввода и не обещая защиты, которой нет.

Факты, на которых основано решение:

- `AssemblyLoadContext` — механизм загрузки и выгрузки сборок, **не песочница**: код в нём имеет все права процесса.
- Отдельный процесс без ограничений ОС тоже **не защищает** от злонамеренного кода: он работает с правами пользователя, может читать файлы, сеть, ставить собственные хуки клавиатуры и т. д.
- Настоящая изоляция (AppContainer, отдельная учётная запись, песочница ОС) в этой фазе не реализуется.

## Решение

1. **Каждый внешний плагин — отдельный процесс.** Backpack запускает собственный исполняемый файл в режиме хоста плагина (`Backpack.exe --plugin-host <папка плагина>`), тот загружает сборку плагина в `AssemblyLoadContext` и общается с Backpack по **ограниченному IPC**: строки JSON через перенаправленные stdin/stdout (не более 64 КБ на сообщение, ограничение частоты). Процесс плагина помещается в Job Object (завершение вместе с Backpack, без дочерних процессов). Сбой, зависание или исключение плагина не роняет Backpack.
2. **Только доверенные плагины.** Перед первым включением показывается явное предупреждение: плагин — программа с правами пользователя; Backpack не может защитить от вредоносного кода, включайте только плагины из источника, которому доверяете. Импорт пакета **не запускает код** и **не даёт доверия**. Доверие хранится в настройках компьютера и не переносится профилями.
3. **Возможности manifest проверяются на границе SDK**, на стороне Backpack, при каждом сообщении. Список permissions без проверок не считается защитой — поэтому он и не выдаётся за защиту: возможности ограничивают то, что *Backpack передаёт* плагину и *что принимает от него*, но не то, что процесс плагина может сделать в системе сам.
4. **Что SDK не выдаёт никогда:** скрытые приватностью события, сырой callback хука, содержимое защищённых полей, текст приложений, заголовки окон, координатную историю. Видимый ввод (`input.visible`) передаётся только **после** фильтра динамической приватности и только плагинам, заявившим эту возможность. Доступ к экрану (`screen`) — отдельная заявляемая возможность; в этой версии хост её **не предоставляет** (запрос отклоняется).
5. **Интерфейс плагинов рисует хост.** Страница настроек описывается схемой в manifest (переключатель, число, текст, выбор) и строится Backpack; плагин получает только значения. Вывод на экран — панель (заголовок, текст, прогресс), которую рисует Backpack (`overlay.panel`).
6. **Устойчивость:** таймаут рукопожатия 5 с; команды — без ожидания ответа; остановка — сообщение `stop`, затем через 2 с принудительное завершение; при отключении снимаются команды, сочетания, панели и подписки. Три сбоя за 10 минут — плагин автоматически отключается с сообщением. Запуск без расширений: параметр `--no-plugins` и переключатель «Безопасный запуск».
7. **Импорт профиля** не устанавливает, не подтверждает доверие и не запускает отсутствующий плагин: ссылки на команды неизвестных плагинов просто не действуют.

## Последствия

- Плагин, запущенный пользователем, может навредить так же, как любая программа, запущенная пользователем. Это сказано в интерфейсе и справке; приложение не называет плагины «безопасными».
- Вредоносный native-код не сдерживается. Для недоверенных плагинов потребуется системная изоляция (кандидат — AppContainer с ограниченными возможностями) — отдельное решение.
- Лицензия SDK и примеров не меняется молча: см. `docs/release/LICENSE-STATUS.md`, раздел «Решения владельца».

## Дополнение: SDK 1.1 — инструменты, которые рисует хост (Phase 4G, 2026-10-30)

Увеличение у курсора, линза и фокус перестали быть встроенными и стали плагинами-примерами. Им нужны изображение экрана и
положение указателя, а модель доверия запрещает отдавать плагинам экран (`screen` не предоставляется) и координатную историю.
Решение — **узкий контракт, в котором пиксели и координаты остаются в процессе Backpack**:

1. `overlay.magnifier` — плагин просит хост открыть увеличение (`OpenMagnifier`: режим `follow`, `pinned` или `region`,
   кратность, размер, оформление). Захват (Magnification API), следование за указателем, выбор области и перемещение
   выполняет хост. Плагин не получает ни кадров, ни координат, ни прямоугольника области.
2. `overlay.dim` — затемнение вокруг области, которую выделяет пользователь (`OpenDim`). Плагин задаёт только оформление.
3. Плагину приходят только события жизненного цикла: `tool.closed` с причиной (`cancelled`, `escape`, `system`, `host`),
   `panel.button`, `OnCommandReleased` для команд с `"hold": true` (отпускание определяет хост опросом сочетания,
   не дольше 5 минут). Хост ограничивает число инструментов (4 на плагин), проверяет каждое сообщение (неизвестный вид,
   идентификатор или режим — отказ, числа приводятся к пределам) и закрывает все окна плагина при Esc, блокировке
   Windows, отключении, удалении и сбое процесса.
4. Панель (`overlay.panel`) в SDK 1.1 получает кнопки, состояние и перемещение. Служебные элементы всех инструментов
   (кнопки, ручки, подписи) показываются при наведении **общим механизмом хоста** (`HoverReveal`); плагин его не реализует
   и не получает событий мыши.
5. Хост не проверяет идентификаторы конкретных плагинов: перенос прежних настроек описан в блоке `legacy` manifest
   (`PluginMigration`) и выполняется только при импорте; он не включает плагин и не подтверждает доверие.

Последствия: любой плагин с этими возможностями может показать увеличение или затемнение поверх экрана — то же видит
пользователь, — но не может прочитать изображение. Процесс плагина по-прежнему работает с правами пользователя и сам
по себе может сделать снимок экрана средствами Windows: контракт ограничивает то, что передаёт Backpack, а не то, что может
программа (см. «Решение», п. 3). Отдельный процесс песочницей не является.
