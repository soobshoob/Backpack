# Первый этап: подключение внешних сервисов

Сайт подготовлен, но публичные сервисы проекта не подключены. Подтверждён только профиль автора GitHub; он не используется как репозиторий или Releases. Microsoft Store, Monobank и Buy Me a Coffee не подставляются из имени пользователя.

Единственная конфигурация: `src/integrations/settings.json`. Пример без секретов — `integrations.example.json`. После второго этапа перенесите подтверждённые значения в settings, выполните тесты/сборку и разместите сайт. Клиентская конфигурация публична: токены, приватные URL и банковские реквизиты в неё не добавляются.

## Каналы и лицензии

- Store: заполнить `store.url` настоящей страницей на apps.microsoft.com и установить `published: true` только после публикации. При `enabled: false` канал скрыт, при отсутствии URL/публикации показано ожидание. Используется неизменённый официальный SVG-бейдж Microsoft с обычной ссылкой, без виджета. Фактически проверены en-us, uk, de и остальные используемые короткие коды. Для Norwegian предусмотрен официальный English fallback. Изображение загружается только при доступном Store-канале; если оно недоступно, остаётся текстовая ссылка на настоящую страницу.
- Releases: заполнить подтверждённые `github.owner` и `repository`. API и обычная ссылка Releases строятся только из этих настроенных значений. Текущий шаблон — `Backpack-{version}-win-x64.zip`, Windows 10/11 x64, portable ZIP. Это не установщик EXE. Изменение платформ/архитектур требует согласованного изменения шаблона и проверок.
- Registry: задать публичный HTTPS `registry.url`, точный GitHub-адрес index.json и адрес инструкции/предложения PR. Пока они null, подготовка JSON работает, а внешние кнопки недоступны.
- Donate: подтвердить точные ссылки `send.monobank.ua/jar/...` и `buymeacoffee.com/...` (допускается www). `enabled: false` скрывает конкретный канал. Неоновая рамка выделяет блок, Monobank оформлен в чёрно-белой палитре, Buy Me a Coffee — в жёлто-чёрной. При null нет активной ссылки. Это добровольная поддержка, не плата за скачивание; скриптов, выбора суммы и формы банковских данных нет.
- Licensing: `licensing.releases` — подтверждённая лицензия **конкретной версии**, а не автоматическая лицензия всех будущих пакетов. Сейчас известен только preview.4 с PolyForm Strict 1.0.0 и отсутствием подписи. Для неизвестной стабильной версии показывается неизвестная лицензия/подпись. SDK и примеры имеют отдельные записи с текущими условиями и признаком ожидаемого решения. Никакой переход на MPL в этом этапе не выполнен. Лицензия записи плагина берётся из самой записи, не из лицензии ядра.

Проверка конфигурации сообщает о неверных доменах, URL, неполной паре owner/repository, неправильном шаблоне и времени кеша. Ошибочные каналы не получают активных ссылок.

## Последний стабильный выпуск

Официальный запрос: `GET https://api.github.com/repos/{owner}/{repo}/releases/latest`, Accept `application/vnd.github+json`, версия API `2026-03-10`, без токена. Сайт дополнительно отклоняет draft, prerelease и теги, не соответствующие согласованному stable-формату `vMAJOR.MINOR.PATCH` или `MAJOR.MINOR.PATCH`.

Принимается ровно один uploaded-asset с точным именем для версии и URL этого же repository/tag. Автоматические zipball/tarball исходников не используются. Первый случайный asset не выбирается. Отсутствие/неоднозначность файла видны в интерфейсе.

SHA-256 берётся из digest выбранного asset. При его отсутствии сайт может прочитать SHA256SUMS.txt, находящийся среди assets **того же выпуска**, и найти точное имя файла. Сумма из другой версии или локального preview не подставляется. При отсутствии опубликованного хеша либо отказе CORS/сети сумма не показывается. Двоичные пакеты браузер для проверки не скачивает. API/JSON/хеш не дают обещания безопасности кода или отсутствия Windows SmartScreen.

Запрос не выполняется на каждом рендере. Общий in-flight запрос дедуплицируется, результаты кешируются в памяти и localStorage на 10 минут; допустимый диапазон конфигурации 1–60 минут. Ошибки сети, HTTP, отсутствие stable/артефакта и 403/429 с ограничением API различаются. Retry-After/RateLimit-Reset учитываются; кнопка временно отключается. Обычная ссылка Releases остаётся доступной независимо от API.

Последний корректный кеш может использоваться при сбое до 7 дней, с датой исходной проверки и заметным предупреждением. Даже свежий кеш подписан как кеш, не как гарантированно последний результат. Проверенная локальная preview.4 вынесена отдельно и не выдаётся за stable или публичный download.

## Реестр: данные и обновление

См. [REGISTRY.md](REGISTRY.md) и [public/registry.schema.json](public/registry.schema.json). Каталог и подробные страницы используют один источник и один кеш. По умолчанию TTL — 5 минут. Посещение каталога/подробностей после истечения TTL или ручная проверка получает свежий index.json. Параллельные запросы объединяются. Уже открытая вкладка не обновляется мгновенно после merge и не опрашивает сервер постоянно.

Сначала валидируется весь документ: версия схемы, уникальность ID/slug, поля, совместимость, URL и ограничения. Некорректные записи не отбрасываются молча по одной. При ошибке показывается причина категории и диагностический путь поля без исходных секретных значений/ответов сервера. Последний валидный кеш может оставаться видимым с предупреждением. Корректный пустой документ заменяет старые записи.

Локальные примеры автора остаются отдельным разделом и не становятся одобренными публикациями. URL назначения определяет действие: `.bppkg` — скачать пакет, release — открыть страницу выпуска. Описания отображаются как обычный текст, без HTML/Markdown execution. SVG и data/blob/file URLs не допускаются как публичные изображения; разрешены PNG/JPEG/WebP по HTTPS.

## Статический хостинг новых slug

При настроенном registry сборка дополнительно создаёт `plugin-route.html` и правило `/plugins/* /plugin-route.html 200` без принудительного override существующих файлов. Сначала обслуживаются настоящие файлы, включая /plugins/publish. Затем неизвестный заранее slug загружает общий shell и ищет запись в реестре. Новая одобренная запись не требует пересборки компонентов.

Для статического хостинга без server-side lookup такая динамическая страница возвращает 200 до проверки реестра; отсутствующий плагин отображается компонентом NotFound после получения данных. Если реестр не настроен, сохраняется настоящий 404 fallback, как раньше. Не заменяйте эти правила SPA-fallback на главную: её prerender не совпадает с shell подробной страницы. Подробности и Nginx-пример — HOSTING.md.

## Проверка без настоящих сервисов

`pnpm test` использует управляемые Response/ошибки. `pnpm dev --mode integration-test --port 5177 --strictPort` включает отдельную фиктивную конфигурацию из tests/fixtures с заметной полосой TEST FIXTURES. `node tests/stage1-browser.mjs` перехватывает все HTTPS-запросы; реальные платежи/аккаунты/релизы не используются. Эти адреса и записи не входят в обычную production-сборку, что проверяется статически.

Проверка режима fixtures не является доказательством существования публичного репозитория, Store-публикации, PR или реальной Банки проекта.

- [Microsoft: HTML-only badge](https://github.com/microsoft/app-store-badge/blob/main/README.md#html-only).
