# Статическое размещение — Stage 1

Ничего не опубликовано. Сборка: `pnpm build`, результат — `Website/dist`.

Сайт рассчитан на корень домена (`base: '/'`). Для подпапки нужно согласованно изменить Vite base, генератор маршрутов, ссылки и rewrite-правила; простое копирование файлов в подпапку не поддерживается.

Генератор создаёт index.html для главной, каталога, публикации, developers и всех шести известных расширений. Дополнительно создаётся `404.html` с оформленной страницей отсутствующего плагина. Поэтому прямые `/plugins/lens`, `/plugins/publish` и обновление страницы работают без dev-сервера.

Сначала хост должен искать реальный файл или index.html каталога. Не переписывайте все неизвестные адреса на главную: её prerender не соответствует странице неизвестного плагина. Без подключённого реестра для отсутствующего маршрута отдавайте `404.html` с кодом 404. Уже сгенерированные страницы должны оставаться с кодом 200.

Для Netlify включён `dist/_redirects`: `/* /404.html 404` (правило без принудительного `!`, чтобы существующие файлы имели приоритет). Для другого сервера настройте аналогичное поведение. Пример Nginx:

```nginx
root /path/to/Website/dist;
index index.html;
location / {
    try_files $uri $uri/index.html =404;
}
error_page 404 /404.html;
location = /404.html { internal; }
```

`tests/static-server.mjs` — локальный файловый сервер QA на 127.0.0.1:5176 с тем же порядком поиска. Он не является производственным сервером и не создаёт backend. Команды:

```powershell
pnpm build
pnpm qa:serve
# в другом терминале:
pnpm test:production
```

Проверка production действительно открывает и обновляет десять адресов, без history fallback Vite. Также проверяются вложенные страницы без JavaScript. Для неизвестного slug предусмотрен компонент NotFound; при размещении требуется сохранить описанный HTTP fallback.

## До настоящей публикации

- Согласовать домен HTTPS, siteUrl и адрес реального проектного репозитория; профиль автора не подменяет репозиторий.
- Опубликовать разрешённые пакеты и записать их настоящие URL, версии, платформы, размеры, даты и совместимость в модель. Локальный ZIP не считается публичной загрузкой.
- Решить условия SDK/примеров. Существующие лицензии не изменены; сайт не выдаёт новое разрешение на производные работы.
- Каталог использует публичный index.json, а публикация — PR и ручной merge владельцем. Автор сам размещает пакет/картинки; помощник готовит валидную запись без загрузки файлов и без административного токена. Нужен подтверждённый registry/catalog/PR URL, не собственный backend сайта.
- При добавлении новых записей обновить статический индекс, данные и сгенерированные маршруты. Рейтинги/сортировки по загрузкам и датам добавлять только при наличии достоверных данных.

Новая инфраструктура, аккаунты, облачное хранилище и административная система в этой работе не создавались.

## Динамические записи реестра

При настроенном registry.url генератор включает /plugins/* → /plugin-route.html 200 (после реальных файлов). Общий shell загружает тот же валидируемый реестр, что каталог. Поэтому новая запись не требует пересборки сайта. Неизвестный slug отображает NotFound после чтения доступных данных; на чисто статическом хосте это HTTP 200 shell, не серверное определение 404 по внешнему JSON. В отключённой конфигурации настоящий 404 сохраняется.

Для Nginx, только после подключения реестра, добавьте перед общим fallback отдельное правило:

```nginx
location ~ ^/plugins/[a-z0-9]+(-[a-z0-9]+)*/?$ {
    try_files $uri/index.html /plugin-route.html;
}
```

Сначала обслуживается существующий /plugins/publish/index.html. Индекс каталога и изображения должны читаться через публичный HTTPS с подходящим CORS. Подробности TTL/ошибок/кеша — INTEGRATIONS.md.
